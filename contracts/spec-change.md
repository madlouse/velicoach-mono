# 规范变更协议

跨产品的协作机制、规范、契约和共享检查脚本只在本仓库定义，也只在这里改；任何项目想改，按这份提，由 Claude 评审。2026-11-13 定。

## 管什么

本仓库的规范、契约、ADR、仓库地图和产品卡，以及各产品仓库里的共享脚本副本（`scripts/check-doc-first.mjs`、`scripts/check-comments.mjs`）。产品仓库只放指向这里的入口块和自己的检查配置 `.velicoach-checks.json`；副本被单独改了，`check-mono-link` 会报出来。只管一个产品的规范（PRD、流水线、技能）在产品仓库按它自己的规则改，不走这里。

## 谁能提，怎么提

任何产品的会话、执行者和评审都能提：在本仓库开 issue（模板「规范变更」），或直接开 PR。写清五件事：

1. **问题：** 在哪个仓库、哪次任务遇到了什么，附链接。
2. **要解决什么：** 改完之后什么会不一样。
3. **影响范围：** 动哪几份文件、哪几个产品仓库、要不要改检查。
4. **建议：** 合并进已有的一条、升级一条，还是新增。
5. **能不能不写文字：** 按[规则怎么定](../standards/rules.md)的顺序回答：能不能从设计上消除（API、架构、目录边界）？不能的话，能不能写成检查（lint、类型、测试、脚本）？都不能，说明为什么只能靠判断。

## Claude 怎么评审

1. **看整体：** 先找已有的相关条目，判定是合并、升级、冲突还是真正的新增；冲突的写明和哪一条冲突、以谁为准。
2. **放对层：** 只管一个产品的退回产品仓库；一类活怎么干的放技能；用户的思考和决策原则放账号记忆和 madlouse/context-infrastructure。
3. **能做成设计或检查的，不收文字：** 只写了文字、却能做成设计或检查的提案退回，请提议者改；确实要判断的，在规则末尾标〔评审：为什么〕。检查的报错要告诉 Agent 去修根因。
4. **守住体量：** AGENTS.md 不超过 4 KB，每份规范一个主题；新增之前先看能不能合并或删掉一条（[ADR-0004](../adr/0004-how-agents-read-the-handbook.md)）。

## 谁来批：必要性原则

Claude 直接批，要同时满足三条：

1. **目的是三类之一：** 让协作更顺（交接、评审、合并少出错）；给一个新场景定规范；补齐体系里缺的一块。
2. **不改定过的事：** 不碰红线，不改产品方向，不推翻产品负责人定过的规则（[变更记录](spec-log.md)里谁批一栏是产品负责人的）。
3. **能撤回，影响小：** 不新增拦合并的关口，不要求每个产品仓库都跟着改流程。

三条有一条不满足，先在频道里和产品负责人讨论，定了再改。批与不批都在 [变更记录](spec-log.md) 记一行。

## 批了以后

同一个 PR 改完本仓库所有同类位置；动到产品仓库的，各开一个 PR，互相链上；跑 `node scripts/check-mono-link.mjs`。要产品负责人亲手做的（比如提交 GitHub Actions 的 workflow），写进 PR 说明。
