# 规范变更协议

跨产品的协作机制、规范、契约和共享检查脚本只在本仓库定义，也只在这里改；任何项目想改，按这份提，由主频道评审并合并。2026-11-13 定。

## 管什么

本仓库的规范、契约、ADR、仓库地图和产品卡，以及各产品仓库里的共享脚本副本（`scripts/check-doc-first.mjs`、`scripts/check-comments.mjs`）。产品仓库只放指向这里的入口块和自己的检查配置 `.velicoach-checks.json`；副本被单独改了，`check-mono-link` 会报出来。只管一个产品的规范（PRD、流水线、技能）在产品仓库按它自己的规则改，不走这里。

## 谁能提，怎么提

任何产品的会话、执行者和评审都能提：在本仓库开 issue（模板「规范变更」），或直接开 PR。写清五件事：

1. **问题：** 在哪个仓库、哪次任务遇到了什么，附链接。
2. **要解决什么：** 改完之后什么会不一样。
3. **影响范围：** 动哪几份文件、哪几个产品仓库、要不要改检查。
4. **建议：** 合并进已有的一条、升级一条，还是新增。
5. **能不能不写文字：** 按[规则怎么定](../standards/rules.md)的顺序回答：能不能从设计上消除（API、架构、目录边界）？不能的话，能不能写成检查（lint、类型、测试、脚本）？都不能，说明为什么只能靠判断。

## 主频道怎么评审

1. **看整体：** 先找已有的相关条目，判定是合并、升级、冲突还是真正的新增；冲突的写明和哪一条冲突、以谁为准。
2. **放对层：** 只管一个产品的退回产品仓库；一类活怎么干的放技能；用户的思考和决策原则放账号记忆和 madlouse/context-infrastructure。
3. **能做成设计或检查的，不收文字：** 只写了文字、却能做成设计或检查的提案退回，请提议者改；确实要判断的，在规则末尾标〔评审：为什么〕。检查的报错要告诉 Agent 去修根因。
4. **守住体量：** AGENTS.md 不超过 4 KB，每份规范一个主题；新增之前先看能不能合并或删掉一条（[ADR-0004](../adr/0004-how-agents-read-the-handbook.md)）。

## 谁来批

主频道代产品负责人批：按产品效果和项目目标判断，产品方向和取舍也由它定（产品负责人 2026-11-13 定）。只有[工程规范](../standards/engineering.md)「分支和合并」第 4 条的三类（撤不回、花钱、对外发声）先在频道里问产品负责人。批与不批都在 [变更记录](spec-log.md) 记一行。

## 合并

本仓库的 PR 由主频道审核后直接合并，不等产品负责人（产品负责人 2026-11-13 定）；各产品频道只提，不合。谁开的 PR 都一样审，包括主频道自己开的和定时巡查发现的。下面六条都满足才合并：

1. **检查都过：** 在 PR 最新的提交并上最新的 main 后，`node scripts/check-mono-link.mjs` 和 `node --test scripts/*.test.mjs` 都通过；GitHub 上的检查也都通过。〔检查：这两条命令〕
2. **说明写全：** PR 正文按模板写了问题、要解决什么、影响范围、判定、怎么守、谁批。〔评审：要判断写清没有〕
3. **记了一行：** 新增或改动的规范都标了怎么守，[变更记录](spec-log.md) 加了一行。〔检查：check-mono-link 查标记；记录行靠评审〕
4. **不冲突：** 和已有规则不冲突；有冲突的，写明以谁为准，旧的那条同一个 PR 改掉。〔评审：要找全相关条目〕
5. **有人批：** 主频道按上面「谁来批」批过；属于三类的，附了产品负责人在频道或 GitHub 上的原话。〔评审：核对原话〕
6. **同类改全：** 动到共享脚本的，产品仓库的同步 PR 已开并互相链上。〔检查：check-mono-link 核对副本〕

只有[工程规范](../standards/engineering.md)「分支和合并」第 4 条的三类（撤不回、花钱、对外发声）不合，在 PR 评论写明原因，再到频道请产品负责人定。产品方向和取舍由主频道代产品负责人定（2026-11-13 定）。

**怎么合：** 合并前在 PR 评论写一行结论：过了，或退回哪一条、为什么；用 squash 合并，标题用 PR 标题；变更记录那一行随 PR 一起进 main。退回的 PR，提的会话改完再审。〔评审：结论写在 PR 评论里〕

## 批了以后

同一个 PR 改完本仓库所有同类位置；动到产品仓库的，各开一个 PR，互相链上；跑 `node scripts/check-mono-link.mjs`。要产品负责人亲手做的（比如提交 GitHub Actions 的 workflow），写进 PR 说明。
