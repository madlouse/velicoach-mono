# Web 验收

E2E 的能力模块之一：在真实浏览器里像用户一样操作网页，做界面验收和功能验收，并留下证据。Veli、主站、种星词现在都是 Web（含 PWA）。

## 两种验收

| | 界面验收 | 功能验收 |
|---|---|---|
| 回答 | 用户看到的对不对：布局、状态、明暗主题、各种屏宽、可达性 | 用户做的事成没成：流程走通，数据和副作用对 |
| 看什么 | 截图、可达性树、对比度和点击区、文案 | 页面上的结果，加上库里的行、发出的请求、邮件和推送 |
| 判据 | 产品的设计系统、design-bar、[设计规范](../standards/design.md) | 案例写的可观察结果 |

一条案例可以两样都验；能力模块把两套手段都备好，案例按需要用。

## 要守住的结果

- **用稳定的把手：** 按可达性角色、标签、`data-` 属性和路由找元素，不按坐标、第几个、样式类名；把手找不到是产品的可达性问题，记下来，不在驱动里绕。
- **真实路径：** 从用户的入口点进去，登录走真实的登录或准备步骤造好的会话；不直接写库让页面「看起来」到了那一步，除非那一步是环境准备（造测试人物）。
- **状态都覆盖：** 每个界面元素的空、加载中、出错、有数据、数据多、文字超长，适用的都有办法到达和判定（`create-verification-skill` 的功能地图写法）。
- **多屏宽和主题：** 至少手机、平板、桌面三种宽度和明暗两套主题；Veli 已有 D1–D5 设备矩阵，沿用。
- **证据完整：** 每条案例留动作前后的截图、失败时的录像和浏览器日志、网络请求摘要；证据和运行编号、提交号、环境一起存。
- **等结果，不等时间：** 等某个元素出现、请求完成或状态变化，不写固定的等待秒数。

工具不限：Playwright、agent-browser、Claude in Chrome 都可以；换工具只改能力模块，不改案例。界面验收可以叠加 design-bar 的 `check_page.py` 和 axe。

线上冒烟用同一套驱动，只是环境、账号和插桩开关不同（[env.md](env.md)）。
