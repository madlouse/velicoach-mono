# E2E 的角色

谁写案例、谁跑、谁修，以及怎么让「为了通过去改源码、改案例、改测试框架」做不到。原则：E2E 只发现问题，修复由写代码的 Agent 做。

## 四个角色

| 角色 | 能改 | 不能改 | 交出 |
|---|---|---|---|
| 案例作者 | 案例 | 源码、能力模块 | 对照 PRD 的案例 PR |
| 能力模块维护者 | 能力模块（环境、驱动、取证、覆盖率） | 源码、案例 | 能力模块 PR，附「同一批案例换模块前后结果一致」的证据 |
| E2E 运行者（含探索） | 不改仓库里的任何文件，只产出运行报告 | 源码、案例、能力模块 | 运行报告、失败的 issue、建议补的案例 |
| 写代码的 Agent | 源码和单元、集成测试 | 案例、能力模块 | 修复 PR，引用失败的 issue，附重跑通过的报告 |

一个 Agent 可以在不同的任务里当不同的角色，但同一个任务、同一个 PR 里只当一个。

## 靠什么守住

1. **路径分组，一个 PR 只碰一组：** 产品在 `.velicoach-checks.json` 的 `roles` 里写源码、能力模块、案例各是哪些路径；`check-role-paths` 发现同一个 PR 改了两组就失败，报错写清怎么拆。和文档先行一样，从目标分支取脚本和配置来跑，PR 改不了这次的判定。〔检查：check-role-paths〕
2. **运行者没有写权限：** 跑 E2E 的子 Agent 定义里不给编辑工具（Claude Code 的 `.claude/agents/*.md` 只列只读工具，或用 `disallowedTools: Edit, Write`）；CI 里运行时用只读的检出，报告写到仓库之外。〔设计：工具层面就改不了文件〕
3. **改案例有依据：** 改案例的 PR 要改了 PRD，或正文有「需求：」引用 PRD 条目；删案例、降门槛、加豁免要产品负责人确认。〔检查：check-doc-first 把案例目录算作代码时生效；删除和降门槛靠产品的合并脚本〕
4. **修复要重跑：** 修复 PR 附集成环境重跑的报告，失败的那条案例和同一个 PRD 条目下的其他案例都要通过。〔评审：合并前的效果评审核对报告〕

现有的产品检查可以直接接上：Veli 的合并闸门已经拦删测试文件、加 `.skip`、改闸门文件；主站的合并闸门拦去掉断言和提前返回；这两条和上面第 1、3 条叠加，不重复。
