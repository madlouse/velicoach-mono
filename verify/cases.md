# E2E 案例

案例写「验什么」：从哪条 PRD 来、用户在什么状态下做什么、看到什么算对。怎么跑由能力模块管，案例里不写选择器、等待和环境细节。

## 一条案例要有什么

| 字段 | 写什么 |
|---|---|
| 编号和 PRD | 案例自己的编号，加它验的 PRD 编号（Veli 的 S、F，主站的 P、F，种星词的 REQ） |
| 环境 | 集成、线上冒烟，或两者 |
| 前提 | 用哪个测试人物、在什么状态（比如「建档完、练了三周、今天是训练日」） |
| 步骤 | 用户做的事，用用户的话写：点什么、说什么、从哪个入口进 |
| 结果 | 用户看得到的结果和该有的副作用，每条都能判对错 |
| 证据 | 要留的截图、录像、日志、库里的行 |

PRD 编号写在测试标题或案例的元数据字段里（比如 `test("S04 第一次训练 …")`），不写在注释里：代码不写注释，检查也只认这两处。

## 从 PRD 推案例

- **每条需求先有一条主路径：** 用户照常完成这件事。
- **用 spec-probes 推边界：** 空、一、多、超长、零和上限、重复提交、中途离开、两个人同时改；每个边界要么在 PRD 里有一句话（就变成一条案例），要么明确不管。PRD 没写的边界先补 PRD，不在案例里自己定答案。
- **推禁止项：** PRD 说「不能」「不会」「只有」的地方，各一条案例证明它真的做不到（权限、隐私、额度、安全回应）。
- **状态多的流程画状态图：** 用 statechart 找到每个状态的最短路径和死路，每个状态至少一条案例能到达。

这几条说的是要覆盖什么，不是写作步骤；Agent 用什么方式推都行，结果按下面的检查判。

## 要守住的结果

- **覆盖：** 每条用户能感知的需求至少一条案例；做不成 E2E 的（纯后台配置、要人工判断的观感）在 `e2eTrace.exempt` 写理由。`check-e2e-trace` 算覆盖率、列出缺的编号；案例引用 PRD 里没有的编号就失败。〔检查：check-e2e-trace〕
- **案例跟着 PRD 变：** PRD 改了验收标准，同一批改案例；改案例的 PR 要么改了 PRD，要么引用 PRD 条目，不能为了让测试通过改结果。〔检查：check-doc-first 和 check-role-paths〕
- **一条案例验一件事：** 失败时从标题就知道是哪条需求坏了。
- **结果写不变量，不写原文：** 「订阅后收到确认邮件」能扛住改版；「第三段文字是某某字」扛不住，除非文案本身就是需求。

## 失败怎么处理

案例失败，跑 E2E 的 Agent 写一份失败报告（案例、PRD 编号、环境、证据、能复现的步骤），开 issue 交给写代码的 Agent，不自己改（[roles.md](roles.md)）。认为是案例错了，同样开 issue，由案例作者对照 PRD 改。
