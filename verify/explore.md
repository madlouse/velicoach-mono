# 探索

案例之外找问题：在集成环境里有边界地乱试，把找到的东西按三条件筛过，再变成案例或 issue。改写自 pstack 的 runtime-probes，去掉了「同一个 Agent 接着写测试、改代码」那一段。

## 先定边界

开始前写下范围（一个 PR、一个功能或整个产品）、入口（走产品的 `verify-<产品>` 驱动；没有驱动就报缺，不另找路子）和停止条件（最多跑多少次、多长时间、碰到什么后果立刻停）。没跑到的探测记「没跑」，不算通过。

## 八类探测

| 类别 | 问什么 |
|---|---|
| 输入不对 | 类型、编码不对，或者多传了不该传的字段会怎样 |
| 大小极端 | 零、一、文档写的上限、远超现实的大小会怎样 |
| 中途打断 | 关掉页面、杀进程、断网，做到一半的事留下什么 |
| 重复和回放 | 连点两次、后退、请求重试会怎样 |
| 状态过期 | 客户端按服务端已经变了的状态操作会怎样 |
| 依赖出错 | 依赖报错、返回空、不见了，用户看到什么 |
| 依赖变慢 | 一次调用花了十秒而不是十毫秒会怎样 |
| 并发 | 两个人同时改同一条记录会怎样 |

## 晋级三条件

每个发现先当假设。三条都满足才算缺陷：

1. **能复现：** 从干净的环境重跑一次，又失败了。
2. **真实用户碰得到：** 写出从哪个真实入口、经过什么路径到这个失败。
3. **值得修：** 后果是用户看得见的、影响数据的，或越过了安全和隐私的边界；内部不整洁不算。

每个发现最后只有一个状态：**确认**（开 issue，并建议一条对应 PRD 的案例）、**驳回**（写理由）、**有保护**（复现了但被某个保护挡住，写下是哪个保护，删掉它时这条会变成真问题）、**升级**（碰到安全、隐私、权限、计费、数据保留而自己判不了，问产品负责人）。

## 交出什么

一份探测记录：每条探测一行，写入口、类别、做了什么、状态、证据编号或没跑的原因。确认的缺陷开 issue 给写代码的 Agent；建议的案例交给案例作者对照 PRD 写进案例。探索的 Agent 不改源码、不改案例（[roles.md](roles.md)）。
