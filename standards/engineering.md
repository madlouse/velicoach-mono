# 工程规范（跨产品）

每个产品仓库都要守的工程底线。产品自己的分层、测试、流水线细则在产品仓库，入口和完成的定义见各自的产品卡。

## 放在哪

| 放在本手册 | 放在产品仓库，挨着代码 |
|---|---|
| 愿景、路线、商业化 | PRD 和需求追溯 |
| 仓库导航和产品卡 | 技术方案和 ADR |
| 跨产品的设计、工程、内容规范和术语 | 设计系统、token 和画板说明 |
| 共享契约和跨产品 ADR | 运行手册、部署和环境说明、`.env.example`（只写变量名，不写值） |
| 任务交接协议 | 产品自己的规范、技能和检查脚本 |

本手册只索引产品仓库里的这些文档（产品卡「去哪读」），不抄一份。〔检查：check-mono-link 核对产品卡的三行和链接〕

## 文档先行

1. **顺序：** 先改 PRD，再改技术方案，再改代码。PRD 和技术方案都在 Git 里，它们的 diff 就是这次的增量需求和增量设计；没有文档改动的功能不开工。〔检查：check-doc-first〕
2. **代码是唯一事实：** 文档是指导，代码是最终的事实。PRD、技术方案和代码说的要一致；发现不一致，在同一个 PR 里改到一致，不留到以后。〔评审：说法一不一致要读懂两边〕
3. **PR 写明依据：** 改产品代码的 PR 满足三条之一：同一个 PR 里改了需求或技术方案；正文有一行「需求：」引用已有的需求（文档路径或需求编号）；正文有一行「免文档：」，类别只能是重构、依赖、修复、测试、构建，并写一句理由。修复只指让行为回到文档写的样子。〔检查：check-doc-first〕
4. **用检查兜底：** 各产品仓库的 `scripts/check-doc-first.mjs` 按第 3 条判定，是本手册同名脚本的原样副本；哪些路径算代码、算文档，写在产品仓库根目录 `.velicoach-checks.json` 的 `docFirst`。合并脚本或 CI 从目标分支取脚本和配置来跑，PR 改不了这次的判定。没有合并脚本的产品用 [checks.workflow.yml](../scripts/checks.workflow.yml) 加一个 CI；Claude 应用没有改 GitHub Actions 的权限，这一步由产品负责人提交。〔检查：check-mono-link 核对副本和配置〕
5. **评审对一致：** 合并前的效果评审核对 PRD、技术方案和代码三者一致（[任务交接协议](../contracts/task.md)）。〔评审：同第 2 条〕

## 分支和合并

1. **只交 PR：** 在工作分支上改，PR 进产品的集成分支；不直接推默认分支、main 或 site。〔检查：Veli、主站的合并脚本只认工作分支；种星词靠评审〕
2. **执行者不合并：** Codex、Antigravity 交 PR 后由 Claude 做效果评审，再按产品的合并规则合并（[任务交接协议](../contracts/task.md)）；进 main 或 site 由产品负责人确认一次。本手册的 PR 由 Claude 按[规范变更协议](../contracts/spec-change.md)「合并」审后直接合并。〔检查：Veli、主站的合并脚本；种星词和本手册靠评审〕
3. **一个 PR 只改一个仓库：** 跨仓库的改动拆成各自的 PR，在 PR 说明里互相链上。〔设计：GitHub 的 PR 只属于一个仓库〕
4. **PR 说明：** 先用仓库自己的模板；没有就写「改之前」「改之后」两段，再写一句怎么做的。〔评审：写得清不清楚要人判断〕

## 结构和代码

1. **先写 ADR 再动结构：** 技术选型、分层和数据结构的变化先在产品仓库写 ADR；跨产品的写在本仓库 adr/。选型坚持极简和最小必要。〔评审：要判断什么算结构变化〕
2. **单一职责、开闭、高内聚低耦合：** 适度抽象，不留死代码，不为想象中的需求扩展。〔评审：要判断抽象得合不合适〕
3. **AI 功能：模型提议，代码裁决。** 数字、安全回应和权限判定只由代码决定；模型负责听懂、看图、推理和措辞，提议要结构化并过代码校验。〔设计：Veli 的 core 是纯函数，依赖方向由 architecture.test.ts 检查〕
4. **兼容性：** 有真实用户或真实安装之前一律以最新为准，不做兼容垫片；之后升级要兼容存量或给迁移。〔评审：要判断有没有真实用户〕
5. **密钥：** 只在服务端环境变量，不进代码、测试、文档和提交信息；`.env*` 不提交。〔检查：.gitignore 挡住 .env*〕
6. **代码不写注释：** 代码是唯一事实，意图写进命名、类型和测试，需求和设计写进 PRD 和技术方案。只有从代码读不出来的外部原因（第三方库的 bug、平台的硬限制）可以留一行 `// why: …`（中文写 `// 为什么：…`）。工具指令（`eslint-disable`、`@ts-expect-error` 这类）和产品配置里允许的机读标记不算注释。各产品仓库的 `scripts/check-comments.mjs` 只查 PR 新增和改动的行：存量注释不追溯，改到哪一行，那一行的注释一起去掉；查哪些路径写在 `.velicoach-checks.json` 的 `comments`，跟文档先行一样从目标分支取来跑。〔检查：check-comments〕
