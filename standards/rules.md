# 规则怎么定、怎么守（跨产品）

加一条规则或纠正一次 Agent 时用：先问能不能从设计上消除或写成检查，最后才写文字；每条规范都标明靠什么守住。思路借鉴 poteto 关于让 Agent 可信的分享：把每次纠正变成确定性的检查。

## 顺序

按 [AGENTS.md](../AGENTS.md)「规则怎么定」的顺序，前一层能解决就不往后走。

1. **先从设计上消除：** 容易用错的东西不给产品代码用，只在封装好的 API 里用；用目录表达边界（比如客户端和服务端、共享代码和应用代码），再用依赖边界检查禁止互相引用。Veli 的分层就是这样做的。〔检查：Veli 的 architecture.test.ts；主站、种星词的边界检查在路线图上〕
2. **再写成检查：** lint、类型、脚本或测试。报错要告诉 Agent 去修根因、改哪里，不给绕过的路；检查的门槛从目标分支取，PR 改不了自己的判定。〔检查：check-doc-first、check-comments 的报错照这样写〕
3. **再做运行时验证：** 让 Agent 把改动跑起来、截图或录屏，看结果对不对。〔评审：还没接成门槛，进路线图〕
4. **最后才写文字：** 只有要判断的事写进 AGENTS.md 或技能；常驻文件只放每次都要守的，其余按任务场景放进技能渐进加载。〔评审：规范变更时 Claude 退回能写成检查却只写了文字的提案〕
5. **放在一层：** 只管一个产品的规则留在产品仓库；跨产品的放本仓库，只在这里改，按[规范变更协议](../contracts/spec-change.md)提；新增前先找已有的相关规则，合并或升级，不另起重复的一条。〔检查：check-mono-link 核对共享脚本副本没被单独改〕
6. **一条意见代表一类问题：** 改完所有同类位置，把原则写回规则、检查或技能；存量里的反模式一起清掉，免得下一个 Agent 照着学。〔评审：同类位置要人找全〕
7. **标明怎么守：** 每条规范末尾写〔设计〕〔检查〕〔验证〕或〔评审〕，写评审的说明为什么还做不成检查。〔检查：check-mono-link〕
